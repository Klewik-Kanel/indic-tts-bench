The whole project, and how to defend it

Written to be read twice. The first pass gives you the argument; the second gives you the numbers, the mathematics and the answer to every question an examiner is likely to reach for.

The project in six sentences

Devanagari writes consonants that carry an unwritten vowel, the schwa. Hindi deletes some of those vowels when it speaks and keeps others, and nothing in the spelling tells you which. The standard fix is a grapheme-to-phoneme front end that applies a deletion rule before the text ever reaches a model. Modern neural text-to-speech is trained end to end and might learn that distinction from audio by itself, in which case the front end is unnecessary engineering. Nobody has measured whether it does, because no published study holds architecture, data, budget, vocoder and evaluation fixed and moves only the input representation. This project builds that measurement, adds Marathi as a same-script control so that the result cannot be confused with a general difficulty of Devanagari, and repeats it across three architectures and five training-data sizes.

The sentence to open with

Say नमक and नमकीन out loud. Both are written with no vowel sign after the second consonant. One is nəmək and the other is nəmkiːn. My question is whether a neural model needs to be told that, or works it out from data.

Part 1

What a text-to-speech system actually is

You will be asked to explain the pipeline before anything else. Keep it to three stages and name what crosses each boundary.

1. Front end

Text in, symbols out. Normalisation, number and abbreviation expansion, then either graphemes straight through or a conversion to phonemes. This is the stage the whole project is about.

2. Acoustic model

Symbols in, an acoustic representation out, normally a mel spectrogram. It has to decide how long each symbol lasts, which is the alignment problem.

3. Vocoder

Mel spectrogram in, waveform out. A mel spectrogram throws away phase, so the vocoder has to invent it plausibly.

The mel spectrogram, and why everyone stops there

A waveform at 22.05 kHz is 22,050 numbers per second. A mel spectrogram takes short overlapping windows of that waveform, takes the magnitude of the Fourier transform of each, and projects the frequency axis onto a mel scale, which is roughly linear below 1 kHz and logarithmic above it because that matches how human pitch perception spaces frequencies. With a hop of 256 samples and 80 mel bins you get about 86 frames per second of 80 numbers each, so you have compressed the signal by a factor of about three while keeping almost everything a listener notices. Splitting the problem at the mel spectrogram means the acoustic model predicts linguistic content and prosody, and the vocoder handles waveform realism, and the two can be trained and swapped independently.

The number to remember for this project: 15 seconds at 22.05 kHz with hop 256 is 1,292 mel frames, which is why the length filter sits at 15 seconds and not higher.

The three architectures in this study are deliberately one from each of the last three families. That is not a survey for its own sake; it is so that a claim about the front end can be stated as holding across generation paradigms rather than as a quirk of one.

Where the front end sits

The front end decides what the model's embedding table is indexed by. With graphemes, the table has one row per Devanagari character and the model must learn from audio that a consonant character sometimes carries a vowel and sometimes does not, and that context decides. With phonemes, the deletion has already happened, so the symbol sequence is closer to what is actually spoken and the model's job is smaller. The question is whether that smaller job produces measurably better speech, and whether the gap depends on how much data you have.

Part 2

Devanagari, the inherent vowel, and the schwa rule

Abugida, not alphabet

Writing systems divide roughly three ways. An alphabet writes consonants and vowels as equal citizens, so Latin writes the a in cat. A syllabary gives each syllable its own sign, as Japanese kana does. An abugida writes consonants as full letters and vowels as marks attached to them, and gives every consonant one default vowel that is not written at all. Devanagari is an abugida and its default vowel is the schwa, ə.

So क is not the sound k. It is kə. To write bare k you add a virama, क्. To write a different vowel you add a matra, so का is kaː and कि is ki. The vowel letters अ आ इ and the rest are used only when a vowel starts a word.

Anusvara is a real decision, not a lookup

The anusvara has no fixed sound. It takes the place of articulation of whatever follows it, so it is n before a dental, m before a labial, ŋ before a velar. The converter resolves it by looking at the next segment, which means the anusvara cannot be handled by a character-to-symbol table. This is one concrete reason the front end has to segment before it maps.

The schwa deletion rule

Hindi deletes many inherent schwas in speech but writes none of the deletions. The rule most implementations use comes from Narasimhan, Sproat and Kiraz (2004): delete a schwa in the context V C _ C V, applied iteratively from right to left. In words, a schwa disappears when it sits between two consonants that each have a vowel on their far side. There is a separate and simpler rule for the word-final schwa, which deletes in Hindi almost unconditionally.

Two things about the rule matter more than the rule itself, and both are things to say when challenged.

The first is that it is iterative, so the order is part of the definition. Deleting one schwa changes the context of its neighbour, which can either enable or block the next deletion. The second is that it runs right to left rather than left to right, because the word-final deletion has to happen first for the rest to come out correctly.

Worked example: नमक, and why order decides it

writtenनमक = n + m + k, three consonants, no vowel signs at all
after segmentationnə mə kə, three inherent schwas made explicit
word-final rulenə mə kə — the final schwa goes
V C _ C V on mright context is now k with no vowel after it, so the pattern fails. The schwa survives.
resultnəmək, namak

Worked example: नमकीन, the same word plus a suffix

writtenनमकीन = n + m + k with an ii matra + n
after segmentationnə mə kiː n — only two inherent schwas, because k already has its vowel
V C _ C V on mleft is ə after n, right is k followed by iː. Pattern matches. Deleted.
V C _ C V on nright is m, which now has no vowel. Pattern fails. Survives.
resultnəmkiːn, namkeen

The pair is the entire thesis in two words. The first three letters are identical; the pronunciation of the second letter is not. No amount of looking at नमक in isolation tells you that.

Worked example: समझना, where a deletion blocks another

after segmentationsə mə dʒʱə naː
rightmost candidate, on dʒʱleft is ə after m, right is n followed by aː. Deleted.
next candidate, on mright is dʒʱ, which has just lost its vowel. Pattern fails. Survives.
resultsəmədʒʱnaː, samajhna, not samjhna

The point of this example

If the rule ran left to right, the m schwa would be evaluated while dʒʱ still had its schwa, the pattern would match, and you would get samjhana. The direction is not a stylistic choice in the implementation. It is what makes the rule correct.

Where the rule is known to fail

  • Morpheme boundaries. A compound or a suffixed form can keep a schwa the rule deletes, because the boundary blocks it. The rule has no access to morphology.
  • Loanwords. Perso-Arabic and English borrowings follow their source phonotactics more than Hindi's.
  • Optionality. Some words have two acceptable pronunciations, which is why the elicitation sheet has a "varies" answer and not only yes and no.

This residual error is why the 49-word stress-test set exists. The set is built from the contexts where the rule is contested, not from typical words, so it measures the part of the problem that is actually hard.

Marathi: the same script with a different rule

Marathi is written in Devanagari and shares almost all of Hindi's phone inventory, but it does not apply medial schwa deletion. It does delete the word-final schwa. That single difference is what makes it the right control: if the phoneme arm beats the grapheme arm by a lot in Hindi and by very little in Marathi, the effect belongs to schwa deletion and not to Devanagari as a script. In the implementation the whole control condition is one boolean flag, delete_medial, which is True for Hindi and False for Marathi. Everything else is the same code path.

Unicode traps, which are not trivia

Combining marks are not alphanumeric

Every matra and the virama are Unicode combining marks, categories Mn and Mc. Python's str.isalnum() returns False for them. Filtering a transcript on isalnum() therefore deletes every vowel sign in the corpus and leaves a bare consonant skeleton, silently. The normaliser filters on unicodedata.category() against an explicit set instead, and there is a named regression test for it.

Composition exclusions

The precomposed nukta consonants U+0958 to U+095F are Unicode composition exclusions, which means NFC will not produce them. A literal pasted into source code is already decomposed, so a table keyed on those literals matches nothing and the nukta handling becomes a silent no-op. The inventory pins the explicit codepoints instead of the literals.

Both of these are worth volunteering. They are the kind of defect that produces a working program with wrong data, which is the failure mode this whole project's apparatus is built to catch.

Part 3

The three architectures, in enough depth to defend the choice

You picked three models from three generative families, all of them current, all of them trainable inside a small GPU budget. Be able to describe each one's generation mechanism, its duration mechanism, and its known weakness.

FastSpeech 2

A non-autoregressive transformer, roughly 27 million parameters. It encodes the symbol sequence, then a variance adaptor predicts a duration, a pitch contour and an energy value for each symbol. The length regulator repeats each encoder output according to its predicted duration to produce a frame-level sequence, and a decoder turns that into a mel spectrogram in a single forward pass.

Its advantage is stability and speed: no autoregression means no skipped or repeated words, and generation is one pass. Its weakness is that it is deterministic, so it predicts an average prosody rather than a sample from the distribution of plausible prosodies, and averaged prosody sounds flat. It also needs durations from somewhere, which is the alignment question in Part 4.

VITS

End to end, roughly 83 million parameters, and the only one of the three that produces a waveform directly with no separate vocoder. Three ideas stacked: a conditional variational autoencoder gives it a latent representation of the audio; a normalising flow makes the prior over that latent expressive enough to match text; and an adversarial loss on the decoder output makes the waveform realistic. Alignment is found by monotonic alignment search during training. Duration at inference comes from a stochastic duration predictor, so two generations of the same sentence differ in rhythm, which is closer to how people actually speak.

The practical fact for this project: the multilingual MMS checkpoints for Hindi and Marathi are VITS models, and they are natively 16 kHz. That is where the sampling-rate confound in Part 7 comes from.

Matcha-TTS

The smallest of the three, roughly 18 million parameters, built on optimal-transport conditional flow matching. Instead of learning to denoise across many diffusion steps, it learns a vector field that transports a simple noise distribution to the data distribution along near-straight paths, and at inference it solves that ODE with a small number of steps. Straighter paths mean fewer steps for the same quality, which is why it is fast despite being in the diffusion family. It uses monotonic alignment search, like VITS, so alignment is internal.

It is the newest of the three and the least studied on Indic languages, which is part of why it is here.

HiFi-GAN, the vocoder

A generative adversarial vocoder, about 14 million parameters in the V1 generator. The generator upsamples a mel spectrogram to a waveform with transposed convolutions, with multi-receptive-field fusion blocks so that several kernel sizes and dilations see the signal at once. Two discriminators judge it: a multi-period discriminator that reshapes the waveform into 2D by several prime periods to catch periodic structure, and a multi-scale discriminator that looks at the waveform at several downsampling rates.

One HiFi-GAN per language is trained on ground-truth mel spectrograms and shared by FastSpeech 2 and Matcha-TTS. That sharing is deliberate: if each acoustic model had its own vocoder, a difference in output could be a difference in vocoder quality rather than in acoustic modelling. VITS bypasses it entirely, which is a real asymmetry and is reported as one.

Why StyleTTS 2 was cut

It is a strong system, and on English benchmarks it is often the strongest. It was removed for compute, not for quality: it needs a style diffusion model and adversarial training with a large speech language model in the loop, which does not fit a 136 GPU-hour budget on free-tier accelerators. If asked, say exactly that. It is future work, and naming a cut honestly is better than pretending the shortlist was purely scientific.

Part 4

Alignment, and why forced alignment was dropped

Alignment is the problem of deciding which audio frames belong to which input symbol. Every acoustic model needs it, and how a model gets it is one of the real differences between the three.

Three ways to get it

External forced alignment

Train or borrow a separate acoustic model, normally a GMM-HMM system such as the Montreal Forced Aligner, and use it to mark phone boundaries in the training audio. The durations then become a supervised target.

Monotonic alignment search

Introduced with Glow-TTS and used by VITS and Matcha-TTS. During training, dynamic programming finds the monotonic alignment between symbols and frames that maximises likelihood under the current model, so the alignment improves as the model does. No external tool.

Internal unsupervised aligner

The approach in Badlani et al., "One TTS Alignment to Rule Them All" (ICASSP 2022). A soft attention alignment is learned jointly with the model and sharpened towards a hard monotonic path. It is what current FastSpeech 2 implementations use in place of external durations.

The decision, and the three reasons in order

Plan v2 had FastSpeech 2 taking durations from the Montreal Forced Aligner. That is now dropped and every model learns alignment internally.

  1. It was an uncontrolled asymmetry between architectures. VITS and Matcha align internally. Giving FastSpeech 2 externally supervised durations hands one architecture information the other two never see, inside a comparison whose subject is the architecture. Whatever the results table then showed about FastSpeech 2 would be partly about its aligner.
  2. It was asymmetric across languages too. MFA publishes a pretrained Hindi acoustic model and no Marathi one. The Marathi arm would have used an aligner trained on 9 hours of its own data while Hindi used one trained on far more, and that difference would sit inside the control comparison, which is the one place it must not be.
  3. It could not run here anyway. montreal-forced-aligner installs from pip, but its Kaldi bindings have no aarch64 Linux wheel and will not build, because MFA ships through conda. Verified, not assumed.

The limitation to volunteer

An internal aligner is generally weaker than MFA at very small data sizes, so the lowest rungs of the ladder may be hurt more than the top ones. That is a property of the ladder worth measuring, not a reason to put the asymmetry back. Say this before someone else does.

Part 5

The metrics, with the mathematics

A metric that is only ever run on real audio tends to be wrong in ways nobody notices until a reviewer asks. Both implemented metrics were checked against answers derivable on paper. Be able to state the formula, say what the measure is blind to, and say what it cannot see at all.

Mel cepstral distortion

MCD measures the distance between two mel cepstra, frame by frame, after aligning them. The mel cepstrum comes from taking the log of the mel filterbank energies and applying a discrete cosine transform, which decorrelates the bands and packs the spectral envelope into the low coefficients.

definitionMCD = K · sqrt( Σd=1..D (cd − ĉd)² ), averaged over aligned frames
the constantK = 10√2 / ln 10
its value6.1419
the sum starts at 1c0 is excluded
alignmentdynamic time warping, because a synthesised utterance is not frame-aligned with the reference

The constant converts the natural-log cepstral distance into decibels and carries the square root of two from the symmetry of the DCT. It is a convention, and every comparable published MCD figure uses it.

Why c0 is dropped, and the test that proves the implementation does

The zeroth cepstral coefficient is the mean of the log mel energies, which is overall loudness. Keeping it makes MCD partly a measure of gain, so a system that is merely quieter scores worse. Dropping it makes the measure blind to gain.

The argument is exact. Scaling a waveform by a constant multiplies its power spectrum by that constant squared. In the log domain that is a constant offset added to every mel band. A constant vector has energy only in the zeroth DCT coefficient. So the whole effect of the scaling lands in c0, and dropping c0 removes it entirely.

Measured

Scaling the input waveform by 0.25 changes the computed MCD by less than 10−6 dB. If that test ever fails, MCD is partly measuring loudness and every MCD number in the paper is suspect.

log-F0 root mean square error

F0 is the fundamental frequency, the rate of vocal fold vibration, which is what you hear as pitch. It is extracted with pyin over a 60 to 500 Hz range, which also labels each frame voiced or unvoiced. The error is computed in the natural log domain over frames that both signals agree are voiced.

The reason for the log is that pitch perception is ratio based, not difference based. A 10 percent pitch error is the same perceptual error whether the speaker sits at 100 Hz or at 300 Hz, but a linear RMSE would call it 10 Hz for one and 30 Hz for the other, so any average across speakers would be dominated by the lower-pitched one. In the log domain a 10 percent error reads as ln(1.1) at both.

Measured

A 10 percent pitch error gives ln(1.1) at both 100 Hz and 300 Hz, exact to 10−12.

Two guards against silent bias

Both of these are small and both are the difference between a metric and a metric you can trust.

  • Mismatched F0 track lengths raise an error rather than being truncated to the shorter. Truncation would systematically favour a system that predicts shorter durations, because the part of the utterance it got wrong would never be scored.
  • A comparison with no commonly voiced frames returns NaN rather than 0.0. Zero would look like a perfect score, so an utterance the system rendered as silence would flatter it.

Alongside the RMSE, the voiced/unvoiced error rate reports how often the two signals disagree about whether a frame is voiced at all. That catches a different failure: a system that gets pitch right where it is voiced but voices the wrong frames.

ASR word error rate, with a floor

Run a speech recogniser over the synthesised audio and compare its transcript with the text that was synthesised. It measures intelligibility, which is the one thing MCD cannot see: an utterance can be spectrally close to the reference and still say the wrong word.

The floor matters. The recogniser has its own error rate on real human speech, so an absolute WER number is meaningless on its own. Run the same recogniser over the ground-truth test audio first, get that figure, and report synthesised WER relative to it. Without the floor you cannot tell a poor system from a poor recogniser.

Predicted mean opinion score

UTMOSv2 and NISQA are neural models trained to predict the score human raters would give. They are cheap, they run over every test utterance, and they track human judgement well enough to rank systems in most cases. They are not a listening test. They were trained mostly on English data and on the kinds of artefacts that were common when they were built, so they can be wrong in a new language or on a new failure mode, and they should always be reported as predicted.

The listening test

The real subjective measure, and the only one that can settle a phoneme-versus-grapheme argument about pronunciation. Every stimulus is low-passed to 8 kHz first so that all systems are heard at equal bandwidth, which is the mitigation for the VITS sampling-rate issue in Part 7. Ground-truth audio is included as an anchor.

Real time factor

Generation time divided by the duration of the audio generated. Below 1.0 is faster than real time. It matters to the thesis because a practitioner choosing between architectures for a low-resource language cares about deployment cost, and because the three models differ by a factor of four in parameter count.

What none of these metrics can see

Worth having ready, because it is a natural follow-up. MCD is an average over frames and will not notice a single mispronounced word in a long utterance. F0 error says nothing about segmental quality. ASR-WER is insensitive to prosody, because a recogniser does not care how naturally a sentence is phrased. Predicted MOS gives one number with no diagnosis. The listening test is the only instrument that hears a schwa in the wrong place and calls it wrong, which is precisely why it is not optional for this project.

Part 6

Experimental design and confound control

This is the part the examiners will actually probe, because it is where a comparison study either holds or falls apart.

One variable at a time

Held constant

  • Training budget: 100,000 steps, 12,000 mel frames per batch, identical learning rate, schedule, warmup, precision and gradient clipping
  • Speaker: one male voice per language, matched on pitch
  • Data: the same frozen, checksummed splits
  • Vocoder: one HiFi-GAN per language, shared
  • Evaluation: the same metrics on the same test set

Varied

  • Input representation: phonemes or graphemes
  • Architecture: FastSpeech 2, VITS, Matcha-TTS
  • Training data quantity: five rungs from 9 hours to 10 minutes
  • Language: Hindi, with Marathi as the control

How "held constant" is enforced rather than remembered

assert_budget_matched() runs every time the 17 configuration files are generated. It compares max steps, batch frames, learning rate, schedule, warmup, precision and gradient clipping across every acoustic-model run and refuses to write configs if any of them differ. A second assertion refuses two runs whose settings hash identically under different run identifiers. If the first ever fails, the comparison is between architectures and budgets at the same time and the results table means nothing. It is an assertion, not a convention.

Each rung is a strict subset of the one above it. The 10-minute set sits inside the 30-minute set, which sits inside the 1-hour set, and so on. That is achieved by ordering the training set once by hash and taking prefixes.

If each rung were sampled independently, the difference between 1 hour and 30 minutes would contain both a data-quantity effect and a sampling-variance effect, and there would be no way to separate them. Since the data-quantity effect is exactly what the ladder exists to measure, independent sampling would have made the ladder measure something other than its own subject.

The control logic, stated as a two-by-two

Say it this way when asked why Marathi:

Large G2P effect in MarathiSmall G2P effect in Marathi
Large in HindiThe effect is about Devanagari generally, or about the normaliser, not about schwa deletionThe effect is about schwa deletion. This is the result the design is built to detect

No other language pairing gives this cleanly. A Hindi-versus-English comparison changes the script, the phonology, the corpus and the resource level at once.

Splits, frozen and reproducible

Membership in test, dev or train comes from a salted SHA-256 of the utterance identifier, not from a seeded shuffle. The difference matters: a seeded shuffle depends on the order in which the manifest happened to be written, so regenerating the manifest can quietly change the test set. Hashing the identifier does not. A rebuild reproduces test.tsv byte for byte.

SPLITS.lock records the salt and a checksum for every file. --verify rehashes them, and rebuilding without --force is refused. Structural checks that run and pass: every ladder rung is a strict superset of the one below, test, dev and train are pairwise disjoint, and every rung lies inside train.

Test is 300 utterances and dev is 100 in each language, held out before any rung is cut.

What counts as a finding

The rule you have set for yourself, and the one to state out loud: no difference smaller than measured seed variance is reported as a finding. With one seed per cell, that variance floor has to come from replicating a single cell and generalising, which is weaker than three seeds throughout. Three seeds everywhere would cost 368 GPU-hours instead of 136. This is the honest argument for institutional GPU access and it is better made openly than defended when challenged.

Part 7

Every decision, with its counter-argument

Each card gives the decision, why it was taken, the strongest objection to it, and a line you can say. Expand as you study; the summaries alone make a revision list.

ScopeSanskrit dropped; Marathi added as a same-script control

Why. The synopsis paired Hindi with Sanskrit. Sanskrit TTS data sits behind a request form with unknown turnaround, so half the study depended on a single access decision outside your control. Worse, the pairing confounded three things at once: language, data quantity and corpus provenance. A difference between the Hindi and Sanskrit arms could have been any of them.

Objection. The approved synopsis said Sanskrit, and changing it looks like avoiding difficulty.

Answer. The replacement is a stronger design, not an easier one. Marathi differs from Hindi in the rule while holding the script, the corpus collection and the resource level fixed, which is what a control has to do. Sanskrit is recorded as future work and the change was approved by the supervisor.

SayMarathi is a better control than Sanskrit because it differs in the phonological rule rather than in the resource level. That is the variable the study is about.
DesignMarathi is a control, not a second target language

Why. The Marathi arm exists to answer one question: is the effect about schwa deletion or about Devanagari. It therefore runs only the two architectures needed for that comparison, not the whole matrix, and it does not get its own ladder.

Objection. Then the study is not really multilingual, and the Marathi result is thin.

Answer. Correct, and it is not claimed to be multilingual. Spending equal compute on Marathi would have bought a second bake-off rather than a cleaner inference about the first. The control needs enough runs to detect a difference in effect size, not a full replication.

Audio22.05 kHz master, with 16 kHz derived for VITS

Why. The synopsis specifies 22.05 kHz, which is the standard rate for TTS training and what HiFi-GAN configurations assume. Both rates are derived from the same gain-corrected 48 kHz source rather than by resampling one from the other, so neither inherits the other's resampling artefacts.

Objection. The MMS VITS checkpoints are natively 16 kHz, so VITS output carries nothing above 8 kHz. Comparing it with 22.05 kHz systems on full-band MCD charges it for missing bandwidth rather than for worse modelling.

Answer. That is exactly right, and the mitigation is built in rather than argued away. MCD is reported in two columns, full band and band-limited to 8 kHz, with the band-limited column as the headline. Listening stimuli are low-passed to 8 kHz for every system, so raters hear equal bandwidth. ASR-WER is unaffected because the recogniser resamples to 16 kHz regardless.

SayThe bandwidth difference is real and I report the band-limited comparison as the headline so it cannot flatter or penalise anyone silently.
AlignmentForced alignment dropped; alignment learned inside every model

Why. Three reasons in order: it gave FastSpeech 2 supervision the other two architectures never receive, inside a comparison about architectures; MFA has a pretrained Hindi model and no Marathi one, which would have put an asymmetry inside the control arm; and its Kaldi bindings do not build on the target architecture.

Objection. MFA durations are more accurate, so you have made FastSpeech 2 worse than it could be.

Answer. Yes, in absolute terms, and that is the correct trade. The study compares architectures under matched conditions, so making one architecture better by giving it information the others lack would destroy the comparison it is part of. Every current FastSpeech 2 implementation uses an internal aligner anyway.

DataMale speaker, speaker 1, in both languages

Why. Hours are equivalent either way: 10.89 and 10.80 hours for the male speakers against 10.73 and 11.19 for the female. Pitch decided it. The two male voices sit 17 Hz apart across the two languages; the female pair are 38 Hz apart. Matching on male leaves less acoustic difference between the Hindi and Marathi arms that has nothing to do with schwa deletion.

Objection. The corpora carry no speaker key, so how do you know which is which, and choosing male is a gender-representation problem.

Answer. The labels were recovered from median F0 over 25 sampled utterances per speaker, and the separation is 90 Hz in Hindi and 111 Hz in Marathi, far wider than any threshold ambiguity. It is reported as an inference from pitch, never as something the dataset says. On representation: the study is single-speaker by design because speaker identity would otherwise be another uncontrolled variable, and which single speaker is chosen is a matched-pair decision, not a claim about voices in general.

DataLength filter 1 to 15 seconds, not 1 to 12

Why. At 1 to 12 seconds no single Hindi speaker reaches a 10-hour top rung: 9.05 and 8.96 hours. At 1 to 15 seconds every candidate clears it. 15 seconds at 22.05 kHz with hop 256 is 1,292 mel frames, which all three architectures handle comfortably.

Objection. Long utterances are usually broken rows, and a 127-second maximum looks like a data error.

Answer. Checked rather than assumed. The 127.7-second item carries 1,600 characters, which is 12.5 characters per second, the corpus median. It is a long read, not a broken row. Transcript quality control found zero misaligned transcripts in either corpus, with characters per second tightly distributed and nothing outside 0.4 to 2.0 times the median.

DataThe ladder's top rung is 9 hours, not 10

Why. Silence trimming cost 5.5 percent in Hindi and 8.4 percent in Marathi, more than the plan assumed, and the frozen test and dev sets take another 1.1 hours between them. What remains is 9.53 hours of Hindi training audio and 9.16 of Marathi. Nine hours is the largest round figure both clear.

Objection. Ten is the number in the plan and a round number reads better.

Answer. Matching the rungs across languages matters more than a round figure. An unmatched top rung would put a data-quantity difference inside the control comparison, which is the one place it must not be.

DesignThe ladder is nested, not independently sampled

Why. Each rung is a prefix of a single hash ordering, so every smaller set is contained in every larger one.

Objection. Independent samples at each size would give a variance estimate for free.

Answer. It would also mix sampling variance into the data-quantity effect, which is the thing the ladder measures. Variance belongs in the seed replication, not in the axis under study.

Front endPunctuation kept as prosody tokens, folded to four marks

Why. Punctuation is the only prosodic signal the text carries, and it appears on roughly one word token in six. Stripping it would remove the model's only cue for phrasing. It is folded to comma, full stop, question mark and exclamation mark so that rare marks do not become near-empty embedding rows.

Objection. Keeping it caused the worst bug in the project.

Answer. It did, and the fix was to peel punctuation from the word edges before the schwa stage and restore it after, not to throw the signal away. Part 8 has the full story. There is now a parametrised invariance test over nine words and four marks in both languages.

Front endOne shared 75-symbol inventory for both languages

Why. Hindi uses 72 of the 75 and Marathi 67, and Marathi's inventory is a strict subset of Hindi's. It is missing only rĩ x ɔː̃ ɣ ɽ, all Perso-Arabic or marginal. Nothing occurs in Marathi that is absent from Hindi, so the control comparison sits in one symbol space with no Marathi-only embedding rows.

Objection. A shared inventory could blur genuine phonetic differences between the languages.

Answer. The subset relation is measured, not assumed, over all 11,044 transcripts. If Marathi had needed symbols Hindi does not have, the two arms would have had different embedding tables and the control comparison would have been weaker.

Known weakness. Marathi has ɽʱ once, z once and q twice across the whole corpus. Those are embedding rows with almost no gradient. Merging nukta consonants for Marathi is the obvious mitigation and is left as a training-configuration decision rather than applied silently.

Front endThe number expander refuses rather than guessing

Why. It expands 0 to 20, the exact tens, 21 to 25, and round hundreds and thousands, and raises an exception on anything else. Digits appear in 15 Marathi utterances and none in Hindi.

Objection. Refusing means losing 15 usable utterances.

Answer. A wrong number word is a pronunciation error baked into the training data and invisible afterwards, because nothing downstream checks it. Fifteen utterances is a cheap price for not corrupting the corpus, and the exception makes the gap visible instead of silent.

MethodGold pronunciations elicited by yes/no/varies, not by IPA transcription

Why. The sheet shows each word with the candidate vowel written in place and numbered, as in n(a1)m(a2)kiin(a3), and asks the speaker whether that specific sound is present. It never shows the rule's prediction. Asking non-phoneticians to write IPA would add transcription noise unrelated to the question being asked.

Objection. The speakers are answering a leading question about a sound you have written down for them.

Answer. The alternative is worse. The merge step turns their yes/no/varies answers into gold forms through the same converter, so the symbols come from the inventory and only the judgement is human. A "varies" option exists precisely because some words have two acceptable pronunciations.

MethodThe project owner cannot be one of the scored speakers

Why. While learning to read the sheet you saw worked answers for नमकीन and समझना, both items in the 49-word set. Anyone who has seen the answers cannot supply an independent judgement on them.

Objection. You are a native speaker and that is a wasted resource.

Answer. Coordinating rather than participating is the cleaner role in any case. The whole value of the gold set is that it was produced by speakers who had not seen the rule's prediction.

ComputeOne seed per cell

Why. Three seeds throughout would cost 368 GPU-hours against 136, which does not fit free-tier accelerators.

Objection. Without replication you cannot tell a real difference from run-to-run noise.

Answer. Agreed, and it is stated as a limitation rather than defended. The rule is that no difference smaller than measured seed variance is reported as a finding, and with one seed per cell that floor rests on replicating a single cell and generalising. This is the honest case for institutional GPU access, and if that access arrives the first thing it buys is seeds, not more architectures.

AudioLoudness normalised to −23 LUFS

Why. ITU-R BS.1770 loudness, the EBU R128 reference level. Peak-normalising instead would leave perceived loudness varying with the dynamics of each utterance, and loudness differences would then appear in the metrics as if they were quality differences.

Verification. Both sample rates land at exactly −23.00 LUFS on a checked sample, the 22.05 and 16 kHz copies agree on duration to under a millisecond, peaks stay under 0.995, and the 50 ms edge padding is present. The peak guard fired once in Hindi, so it is not dead code.

ComputeFree-tier Kaggle accelerators with checkpoint resume

Why. No institutional GPU access at the time of planning. Kaggle gives a fixed weekly quota with a session time limit, so the cost of a killed session has to be bounded.

Objection. Sessions get killed and quota runs out, so this is fragile.

Answer. Which is exactly why resume-from-checkpoint is verified before any real training. The smoke test pushes a checkpoint to the Hub, deletes it locally, pulls it back and compares SHA-256, because an untested resume path is not a safety net. It also checks that a GPU is actually attached, which on a non-verified account it silently is not, and measures a fixed fp16 matmul so that the step budget comes from a measurement rather than a guess.

ScopeStyleTTS 2 cut from the architecture list

Why. Compute. Style diffusion plus adversarial training with a large speech language model in the loop does not fit the budget.

Objection. It is currently among the strongest systems, so the comparison is missing the best model.

Answer. True, and it is listed as future work. The study's claim is about the front end's contribution across generation paradigms, and three paradigms are already represented. Adding a fourth model would have cost roughly a third of the budget and bought no new paradigm.

Part 8

Three defects, and why they are your best evidence

A progress review that lists only completed tasks says nothing about rigour. Volunteering a bug that would have corrupted the headline result, and explaining how it was caught, is the strongest thing you can show. None of these three was found by the unit tests. All three were found by running the apparatus over real data or by watching a person use it.

One: punctuation was rewriting words

Punctuation was kept as a prosody token, which was right, but it stayed attached to the word through the schwa stage, which was wrong. The failure is double. A trailing comma means the word-final schwa is no longer word-final, so the final-deletion rule does not fire and the schwa survives. That survival then supplies the right-hand vowel that lets the schwa to its left delete. So नमक is nəmək but नमक, came out nəmkə, which is a different word.

16.5 percent of Hindi word tokens and 14.9 percent of Marathi carry punctuation. The corruption would have fallen on the phoneme arm alone, because the grapheme path never touches the schwa stage, so the phoneme-versus-grapheme comparison would have been measuring the bug. Punctuation is now peeled from the word edges before the schwa stage and restored after, with a parametrised invariance test over nine words and four marks in both languages.

Two: a training run was in the plan twice

The ladder's 9-hour rung was a second copy of the main run. r01 and r07 trained the same architecture on the same data under the same budget and would have cost 10 GPU-hours to produce a number already in hand. It was invisible because the run identifier sat inside the configuration hash, which makes two identical runs look distinct.

Run identifier is now excluded from the hash and an assertion refuses two runs whose settings hash identically. The plan went from 19 runs and 146 GPU-hours to 17 and 136.

Three: the elicitation sheet leaked its own answers

The three worked examples at the top of the sheet were घर, नमकीन and कमल. All three were items in the 49-word test set, so the sheet was handing every participant the correct answers to three of the words it was about to test them on, and nothing in the merge would have flagged it. Replaced with कपड़ा, बर्तन and पानी, which cover a deletion, a retention and a word with no slots at all. check_examples_are_outside now runs at sheet-generation time and refuses to write a sheet whose examples appear in the set.

A fourth, worth mentioning if instruments come up

Before that, the sheet itself was misread by its first reader. On नमकीन shown as n[1]m[2]kiin[3], the reader took the numbered blanks to be asking whether a vowel exists anywhere in that syllable, so slot 3 was nearly marked yes because of the written ii, and slot 1 was nearly marked no even though the word is pronounced with an audible a. Both errors are silent, and with two or three speakers reading it the same way the gold set would have been confidently wrong. The sheet now writes the candidate vowel in place as n(a1)m(a2)kiin(a3), states that plainly written vowels are not in question, and carries worked examples. An instrument needs piloting on a real reader, not just unit tests.

Part 9

Weaknesses to volunteer before you are asked

Saying these first is worth more than defending them later. Each one has a reason it is acceptable and a sentence that says so.

The 49 gold pronunciations are not yet validated

The rule scores 49 out of 49 against the gold set, and that figure is not a result. The rule implementation and the gold forms were written by the same person in the same sitting, so the number measures self-consistency. The scorer refuses to report a validated figure until independent speakers have checked the items.

One seed per cell

The variance floor rests on replicating one cell and generalising. No difference smaller than that floor is reported as a finding.

Rare phones in Marathi

Three phones occur fewer than three times in the whole corpus, so those embedding rows receive almost no gradient. Merging nukta consonants for Marathi is the mitigation and is a configuration decision, not something applied silently.

The internal aligner at small data sizes

Weaker than forced alignment when data is scarce, so the lowest ladder rungs may suffer more than the top ones. That is something the ladder can measure.

Single speaker, single style

One voice per language and read speech only. Nothing here generalises to conversational speech or to speaker variation, and it is not claimed to.

VITS is not vocoder-matched

FastSpeech 2 and Matcha share a HiFi-GAN; VITS generates its waveform itself. That asymmetry is inherent to the architecture and is reported rather than papered over.

Predicted MOS is not MOS

UTMOSv2 and NISQA were trained mostly on English and on older artefact types. They are reported as predicted and the listening test is what settles subjective claims.

Nothing has been trained yet

Everything established so far is a property of the corpus, the front end or the measuring apparatus. That is deliberate sequencing, but the training wrappers are still to be written and they need no GPU.

Part 10

Question bank

Grouped by the kind of person asking. Collapsed so you can test yourself: read the question, answer it out loud, then open it. Filter by any word to drill a topic.

The phonetician

PhoneticsIs schwa deletion not a solved problem?

The rule is well studied and has been since 2004. What is not studied is whether a modern end-to-end model needs the rule at all. Those are different questions, and the second one is mine. If the models absorb it, everyone building Indic TTS can stop maintaining a front end; if they do not, the field should stop defaulting to character input.

PhoneticsWhy right to left, and does the direction actually matter?

It matters and there is a worked case. In समझना, deleting the schwa on dʒʱ first removes the right-hand vowel that the m schwa would have needed, so the m schwa is blocked and you get samajhna. Left to right you would evaluate m first, find a vowel on both sides, delete it, and get samjhana, which is wrong. The word-final deletion also has to happen before the medial rule for नमक to come out as namak.

PhoneticsWhat about the cases the rule gets wrong?

Residual errors cluster at morpheme boundaries, where a compound or a suffix blocks a deletion the rule takes, and in loanwords, which follow their source phonotactics. The rule has no morphological information. That residual is exactly why the 49-item set is built from contested contexts rather than typical words, and why the elicitation sheet has a "varies" option.

PhoneticsWhy not just use a pronunciation lexicon?

A lexicon does not generalise to unseen words, and Hindi is morphologically productive, so out-of-vocabulary rates on running text are high. The front end does support a lexicon override for known exceptions, which is the right place for the irregular cases, but the rule has to handle everything else.

PhoneticsHow does the front end handle the anusvara?

By looking at what follows. The anusvara has no fixed sound; it takes the place of articulation of the next consonant, so it is n before a dental, m before a labial, ŋ before a velar. That is a segmentation-stage decision, which is one of the reasons the converter segments before it maps rather than using a character table.

PhoneticsMarathi really has no medial schwa deletion at all?

Not as a productive rule of the kind Hindi has. It does delete the word-final schwa, which is why the control condition switches off medial deletion and leaves final deletion on. If someone argues about marginal cases, the answer is that the control does not require Marathi to have zero deletion; it requires the effect to be much smaller, which is what the design detects.

The machine learning examiner

ModelsWhy these three architectures and not others?

One from each current generative family: non-autoregressive with explicit durations, flow-based end to end, and flow matching. That lets the conclusion be stated as holding across paradigms rather than as a quirk of one design. All three fit the compute budget. StyleTTS 2 was cut for compute and is named as future work.

ModelsVITS has three times the parameters of the others. Is that fair?

The budget that is held equal is the training budget, not the parameter count: identical steps, batch frames, learning rate, schedule, precision and clipping. Equalising parameters instead would mean training a different VITS from the one anyone actually uses. The comparison is between architectures as they are deployed, and parameter count is part of what an architecture is. It is also why real time factor is reported.

ModelsHow do you know the training budgets really are identical?

assert_budget_matched() runs every time the configuration files are generated and refuses to write them if any budget field differs across acoustic runs. A second assertion refuses two runs whose settings hash identically under different identifiers, and that one already caught a duplicated run worth 10 GPU-hours. It is enforced, not remembered.

ModelsWhy not fine-tune from a pretrained checkpoint everywhere?

VITS does initialise from the MMS checkpoints, which is what makes the low rungs of the ladder feasible at all for it. The complication is that MMS is natively 16 kHz, so that arm carries a bandwidth difference, and the MCD reporting and the listening stimuli are both set up to neutralise it. For the other two there is no comparable Indic checkpoint, so pretraining is a property of the architecture arm rather than a variable I could hold fixed.

ModelsWhat if the grapheme model just learns the rule from audio?

That is one of the two outcomes the study is built to detect and it is a useful result, not a failure. It would mean that for Hindi, front-end engineering is optional above some data threshold, and the ladder tells you where that threshold is. The Marathi control then tells you whether the same holds when the rule is easier.

ModelsIs 100,000 steps enough?

It is enough for all three to converge on 9 hours of single-speaker data, which is what the published recipes indicate, and the smoke test measures actual throughput so that the step budget rests on a measurement. The stronger point is that it is the same for every run, so a difference in the results table cannot be a difference in training length.

The reproducibility and systems examiner

MethodHow do I reproduce a number in your results table?

Every results row carries a run identifier and a configuration hash, and every run is a YAML file in configs/. The splits are frozen with a salted SHA-256 over utterance identifiers, recorded in SPLITS.lock with a checksum per file, and --verify rehashes them. A rebuild reproduces test.tsv byte for byte.

MethodWhy hash the identifier instead of using a seeded shuffle?

A seeded shuffle depends on the order in which the manifest happened to be written, so regenerating the manifest can quietly change the test set. Hashing the utterance identifier does not depend on order at all, which is what makes the split reproducible across machines and across rebuilds.

MethodWhere did your corpus figures come from?

Measured over the full corpora, not from the dataset cards, which state neither hours nor speaker count nor sampling rate. The first estimate was extrapolated from 50 utterances and was 19 percent low for Hindi, 21.99 hours against 26.23 actual. That is recorded in the results log and it is the reason no figure in the report comes from a sample.

MethodWill this run on someone else's machine?

The training jobs are configuration files and a wrapper, and checkpoint resume is verified by round-tripping a checkpoint to the Hub and comparing SHA-256. The one thing that is not portable is the free-tier accelerator quota, which is why the plan is chunked into resumable runs rather than long single sessions.

The statistics examiner

StatsOne seed. How do you know any difference is real?

I do not, beyond the variance floor, and I say so. The rule is that no difference smaller than measured seed variance is reported as a finding, and with one seed per cell that floor comes from replicating a single cell and generalising, which is weaker than three seeds throughout. Three seeds everywhere is 368 GPU-hours against 136. If institutional GPU access arrives, seeds are the first thing it buys.

StatsWhat is your test set and is it large enough?

300 utterances per language, held out before any ladder rung is cut, with 100 more for development. For objective metrics that is ample. For the listening test the relevant number is raters times items, not corpus size, and the stimulus set is a subset chosen to include the contested-schwa cases.

StatsHow will you test significance?

For objective metrics, paired comparisons over the same test utterances, since both systems see identical inputs, with the seed variance as the floor below which nothing is claimed. For listening test scores, a mixed-effects treatment with rater and item as random effects is the appropriate form, because raters differ systematically and items differ in difficulty.

StatsTwo or three speakers for the gold set is a very small panel.

It is, and the design accounts for it. The sheet has a "varies" option, disagreement between speakers is detected at the slot level rather than being averaged away, and an item on which speakers disagree is reported as variable rather than resolved. The panel is validating a rule's predictions on 49 contested items, not estimating a population parameter.

The supervisor and scope questions

ScopeYou changed the synopsis. Why should I accept that?

One change, made for a design reason and approved. The Hindi-Sanskrit pairing confounded language, data quantity and corpus provenance at once, and Sanskrit data was gated behind a request with unknown turnaround, so half the study depended on someone else's decision. Marathi holds script, corpus collection and resource level fixed and differs in the rule, which is what a control has to do.

ScopeNothing is trained yet. Are you behind?

The sequencing is deliberate: everything established so far is a property of the corpus, the front end or the measuring apparatus, and each of those had to be right before any GPU time was spent. The apparatus has already caught three defects that would have corrupted results. What remains before training is the four model wrappers, and none of that needs a GPU.

ScopeWhat do you do if the result is null?

Report it. A well-controlled null is a real contribution here, because it tells practitioners they can stop building and maintaining a front end for Hindi. The ladder makes the null more informative, not less, because it says at which data size the front end stops mattering.

ScopeWhat would DGX access change?

First, three seeds per cell instead of one, which turns the variance floor from an assumption into a measurement. Then the full architecture matrix on the Marathi arm, and StyleTTS 2 back in the comparison. Wall-clock is the smaller gain; the statistical strength is the real one.

The "so what" questions

ImpactWho actually uses this result?

Anyone building TTS for a Devanagari-script language with limited data, which is most of the Indic language space. The concrete question they face is whether to spend weeks building and maintaining a G2P front end. Today that decision is made by convention. This gives them a measured answer, split by architecture and by how much data they have.

ImpactWhat is released?

The contested-schwa stress-test set with speaker-validated gold pronunciations, which does not currently exist; the configuration-reproducible testbed; and fine-tuned checkpoints for both languages. The stress-test set is the piece most likely to be reused by others, because it is the part that is hard to build and easy to share.

ImpactDoes this generalise beyond Hindi and Marathi?

The method does, and the specific finding does not without testing. The design is the contribution as much as the numbers: hold everything fixed, move only the input representation, add a same-script control that differs in the rule. That pattern transfers to any orthography with an implicit phonological process, and Devanagari has several beyond schwa deletion.

Part 13

What comes next

If asked what remains, answer in this order. The first block needs no GPU, which is the point.

  1. Four training wrappers for FastSpeech 2, VITS, Matcha-TTS and HiFi-GAN, each reading a run configuration and writing resumable checkpoints.
  2. The remaining evaluation harness: ASR word error rate with its ground-truth floor, predicted MOS through UTMOSv2 and NISQA, and real time factor.
  3. Analysis code: tables, plots and the statistical treatment, written before the numbers arrive so that the analysis is not chosen after seeing them.
  4. Listening test infrastructure, with 8 kHz low-passed stimuli and a ground-truth anchor.
  5. Blocked on people: elicitation sheets from two or three native Hindi speakers, which is what turns the 49-item set from self-consistent into validated.
  6. Blocked on a round trip: the Kaggle smoke test, which verifies that a GPU is attached, measures throughput, and proves a checkpoint survives push, delete and pull with matching SHA-256.

The closing line

Whichever way the result goes it is useful. If the architectures absorb schwa deletion, nobody needs to build the front end again. If they do not, the field should stop defaulting to character input for Indic languages.
